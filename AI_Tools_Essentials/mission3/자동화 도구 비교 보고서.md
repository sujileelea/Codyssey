# 자동화 도구 비교 구현 보고서 (Activepieces vs Pipedream)

## 1. 사용한 도구

| 항목 | Activepieces | Pipedream |
|---|---|---|
| 형태 | 오픈소스(MIT) 노코드 빌더. **Cloud 무료 플랜** 사용(자가호스팅도 가능) | 서버리스 워크플로우 SaaS. **Free 플랜** 사용 |
| 플랜(실측) | Free — 카드 등록 없음, 일일 크레딧 갱신 | Free — 월 100 credits(1 credit = 30초 연산), 활성 워크플로우·연결 계정 수 제한, 이벤트 이력 제한 |
| 워크플로우명 | `P1 링크 본문 추출 (Activepieces)` | `P1 링크 본문 추출 (Pipedream)` |
| 연동 | Slack(Lea-Loft 워크스페이스) `#link-inbox`, HTTP(jina reader) | 동일 |

### 두 도구를 선택한 이유

| 도구 | 선택 이유 | 이번 미션에서 확인하려는 차이 |
|---|---|---|
| Activepieces | 무료 플랜에서도 Router로 여러 조건 경로를 만들 수 있고, 오픈소스 Community Edition을 셀프호스팅할 수 있다. Slack·HTTP뿐 아니라 Gemini·GitHub 피스도 제공해 프로젝트 1의 링크 본문 추출을 프로젝트 2의 AI 요약·발행 흐름으로 자연스럽게 확장할 수 있다. | 시각적 캔버스, 무료 다중 분기, 실행 경로 표시, 셀프호스팅 가능성이 실제 자동화 설계에 주는 이점을 확인한다. |
| Pipedream | 무료 플랜에서 Slack 즉시 Trigger와 HTTP Action을 제공해 Activepieces와 동일한 워크플로우를 구현할 수 있다. 입력 필드의 JavaScript 표현식과 이벤트 Replay를 지원하므로 노드 중심 노코드 도구와 다른 API·코드 중심 접근을 비교하기 적합하다. | 세로 단계형 빌더, JavaScript 데이터 가공, Filter 기반 분기, 이벤트 재현 방식이 구현 속도와 디버깅에 주는 차이를 확인한다. |

## 2. 공통 워크플로우

**업무**: Slack 채널에 링크를 올리면 링크를 열어 본문을 가져오고, 읽을 수 있었는지에 따라 같은 메시지의 스레드에 결과를 달아 준다. (프로젝트 2 "링크 → AI 요약 → Lea-Loft 발행" 파이프라인의 앞부분.)

```text
Slack #link-inbox 새 메시지                       ← Trigger (Events API, 즉시)
  → URL 추출 (메시지 텍스트 <url|표시> 형식에서)
  → Action 1: 본문 추출 — GET https://r.jina.ai/{url}   (키 없이 본문을 마크다운으로)
  → 조건 분기: 본문 추출 성공?  (응답에 "Warning: Target URL returned error"가 없음)
      ├ 성공 → Action 2: 스레드 답글 "✅ 본문 추출 성공 — 제목"
      └ 실패 → Action 3: 스레드 답글 "❓ 본문 추출 실패 — 직접 확인 필요"
```

- 성공 경로 테스트 링크: 일반 문서 페이지(Wikipedia `Automation`, n8n 문서)
- 실패 경로 테스트 링크: YouTube(로그인 벽 → jina가 401 경고 반환)
- 두 도구가 같은 채널을 보므로 링크 하나에 답글이 도구별로 하나씩(총 2개) 달린다. 서로의 답글에 다시 반응하지 않도록 봇·스레드 메시지는 무시한다(§3).

### 구현 대응표

| 단계        | Activepieces                                                                                                        | Pipedream                                                                                                       |
| --------- | ------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Trigger   | Slack – **New Message Posted to Channel** (채널 ID 지정, `Ignore Bot Messages` 켬)                                       | Slack – **New Message In Channels (Instant)** (`Ignore Bots`·`Ignore replies in threads` 켬)                     |
| URL 추출    | **Text Helper – Find** 피스, 정규식 `https?://[^\s\|>]+`                                                                 | 별도 단계 없음 — HTTP 단계 URL 필드에 **JS 표현식** `{{steps.trigger.event.text.split('<')[1].split('\|')[0].split('>')[0]}}` |
| 본문 추출     | **HTTP – Send HTTP request** GET, 헤더 `Accept: text/plain`                                                           | **HTTP / Webhook – Send GET Request**                                                                           |
| 분기        | **Router** 3분기: ① `본문 추출 성공`(body가 Warning 미포함 AND 텍스트에 http 포함) ② `링크 없음(무시)`(텍스트에 http 없음, 빈 분기) ③ Otherwise = 실패 | **Filter** — `End if` 본문이 "Warning: Target URL returned error" **포함**하면 종료. 답글 문구는 답글 단계에서 **삼항식**으로 성공/실패를 나눔  |
| 성공 Action | Slack – Send Message To A Channel (Reply to Thread = 트리거 ts)                                                        | Slack – Reply to a Message Thread → Filter 통과 → Slack – Add Emoji Reaction(`:link:`)                            |
| 실패 Action | Otherwise 분기의 Slack – Send Message(❓ 문구)                                                                            | 같은 답글 단계가 ❓ 문구로 게시 → Filter에서 종료                                                                                |
| 무료 분기 방식  | Router에서 여러 경로와 Otherwise를 직접 구성                                                                                    | If/Else·Switch 대신 무료 Filter와 조건부 답글 문구를 조합                                                                      |

### 실행 결과 (실측, 2026-08-27 00:20~00:24)

| 도구 | 성공 경로 | 실패 경로 |
|---|---|---|
| Activepieces | Wikipedia 링크 → `본문 추출 성공` 분기 실행 → 스레드 답글 (Run 7s) | YouTube 링크 → `Otherwise` 분기 실행 → ❓ 답글 (Run 12s) |
| Pipedream | Wikipedia 링크 → 답글 ✅ → Filter 통과 → `:link:` 리액션 (7.6s) | YouTube 링크 → 답글 ❓ → Filter **EXIT** (8.2s) |

## 3. 구현 과정 요약

| 구현 단계 | Activepieces | Pipedream |
|---|---|---|
| 1. Trigger | Slack `New Message Posted to Channel`을 연결하고 `#link-inbox`를 지정 | Slack `New Message In Channels (Instant)`를 연결하고 같은 채널을 지정 |
| 2. 이벤트 제외 | 봇 메시지를 무시하고 URL이 없는 메시지는 처리 경로에서 제외 | 봇 메시지와 스레드 답글을 무시해 자동화끼리 다시 반응하지 않도록 설정 |
| 3. URL·본문 처리 | Text Helper로 URL 추출 → HTTP GET으로 jina reader 본문 수집 | Trigger 데이터의 URL을 JavaScript 표현식으로 추출 → HTTP GET으로 동일 본문 수집 |
| 4. 조건 분기 | Router에서 본문 추출 성공·링크 없음·실패 경로 구성 | 조건부 Slack 답글 뒤 Filter에서 성공은 통과하고 실패는 종료 |
| 5. 결과 Action | 성공 또는 실패 문구를 원 메시지의 Slack 스레드에 답글 | 성공 또는 실패 문구를 스레드에 답글하고 성공 경로에는 이모지 반응 추가 |
| 6. 검증 | Publish 후 성공·실패 링크로 각 경로의 실행 로그와 Slack 답글 확인 | Deploy 후 같은 링크로 Filter 통과·종료 로그와 Slack 답글 확인 |

## 4. 비교 항목 (8개)

| # | 비교 항목 | Activepieces | Pipedream |
|---|---|---|---|
| 1 | **트리거 방식** | Slack Events API 즉시 트리거. 봇 메시지 무시 옵션 내장 | 동일하게 즉시. `Ignore Bots`·`Ignore replies in threads` 두 옵션 제공 |
| 2 | **조건 분기** | **Router** — 분기 N개 + Otherwise, 분기별 AND/OR 조건, 무료 | **Filter**(통과/종료)만 무료. **If/Else·Switch는 유료(Advanced)** |
| 3 | **데이터 매핑·표현식** | 데이터 선택기로 토큰 삽입(직접 타이핑 불가). 문자열 가공은 Text Helper 등 **피스**로 | 필드 안에 **JS 표현식** 자유롭게(`split`, 삼항식 등). 정규식 리터럴 일부 파싱 제약 |
| 4 | **연동·확장 방식** | Slack·HTTP·Gemini·GitHub 등을 피스로 연결하며 Community Edition에서도 확장 가능 | 사전 제공 액션과 코드 스텝을 함께 사용해 API 중심 통합에 유연함 |
| 5 | **실행 로그·디버깅** | Runs 목록 → 캔버스 위에 단계별 Succeeded/Failed와 분기 경로가 그려짐. 단계 입력/출력 열람 | Live Events 목록 → 이벤트별 단계 결과와 Filter EXIT 표시. `Build from event`·`Replay event`로 재현. 무료는 이력 보존 제한 |
| 6 | **에러 처리** | 실패 단계와 입출력을 Runs에서 확인하고 해당 실행을 다시 시도할 수 있음 | 실패 이벤트를 Live Events에서 확인하고 Replay할 수 있으며 자동 재시도는 유료 기능 |
| 7 | **무료 플랜 한도** | 카드 없음, 일일 크레딧. 이번 P1(실행 8회)로 한도 체감 없음 | 100 credits/월. P1 실행 후 크레딧 소모 확인 가능(1회 실행 ≈ 1 credit) |
| 8 | **빌더 UX·이식성** | 캔버스형이라 분기 구조를 시각화하기 좋고 플로우 JSON Import/Export를 지원 | 세로 단계형이라 단순 흐름을 읽기 쉽고 워크플로우 복제·프로젝트 단위 관리를 지원 |

## 5. 각 도구의 장단점

| 도구 | 장점 | 단점 |
|---|---|---|
| Activepieces | 무료 Router로 다중 경로와 Otherwise를 구성할 수 있음<br>실행 경로가 캔버스에 표시돼 분기 결과를 확인하기 쉬움<br>오픈소스 Community Edition 셀프호스팅 가능<br>Gemini·GitHub 등 프로젝트 2 확장에 필요한 피스 제공 | 문자열 가공에 Text Helper나 Code 등 별도 단계가 늘어날 수 있음<br>복잡한 캔버스는 노드 수가 많아지면 한 화면에 보기 어려움 |
| Pipedream | 입력 필드에서 JavaScript 표현식을 사용해 데이터 가공이 유연함<br>Slack 액션이 스레드 답글·리액션 등으로 세분화됨<br>Replay와 Build from event가 이벤트 재현에 유용함 | 무료 플랜은 If/Else·Switch 대신 Filter 중심으로 구성해야 함<br>고급 분기·자동 재시도·긴 실행 이력에는 유료 기능이 필요함<br>월간 무료 크레딧 때문에 반복 테스트 횟수를 관리해야 함 |

## 6. 어떤 상황에 적합한가 (의견)

| 상황 | 권장 도구 | 이유 |
|---|---|---|
| 두 개 이상의 조건 경로마다 서로 다른 Action이 필요한 경우 | Activepieces | 무료 Router에서 다중 분기와 Otherwise를 직접 표현할 수 있음 |
| 워크플로우를 시각적으로 설명하거나 팀에 인수인계해야 하는 경우 | Activepieces | 캔버스와 실행 로그에 실제 경로가 표시됨 |
| 추가 서비스 비용 없이 자체 서버에서 장기 운영하려는 경우 | Activepieces Community Edition | 오픈소스 셀프호스팅이 가능해 Cloud 실행 크레딧 의존도를 줄일 수 있음 |
| JavaScript를 이용한 데이터 변환과 API 조합이 많은 단순 경로 | Pipedream | 입력 필드 표현식으로 별도 단계 없이 데이터를 가공할 수 있음 |
| 과거 이벤트를 재현하며 API 응답을 디버깅해야 하는 경우 | Pipedream | Replay와 Build from event 기능이 편리함 |
| 이번 프로젝트 2: Gemini 요약·분류 → 조건 분기 → GitHub 발행 → Slack 답글 | **Activepieces** | 무료 다중 분기, Gemini·GitHub·Slack 연동, 셀프호스팅 가능성이 모두 필요함 |

## 7. 유료 기능 사용 여부

| 구분 | 사용 범위 | 유료 기능 대체 방식 |
|---|---|---|
| 프로젝트 1 | Activepieces Free, Pipedream Free, Slack 무료 워크스페이스, jina reader | Pipedream If/Else 대신 Filter와 조건식을 사용하고 자동 재시도는 사용하지 않음 |
| 프로젝트 2 | Activepieces Community Edition, Gemini 3.5 Flash-Lite 무료 티어, Slack, GitHub, jina reader | Lea-Loft Mac mini에 셀프호스팅해 Activepieces Cloud 크레딧 의존도를 제거할 계획 |
| 결제 여부 | 유료 기능 및 유료 API 사용 없음 | 무료 범위의 제한은 설계와 조건 분기로 보완 |

## 8. 보안 처리

| 보안 항목 | 처리 내용 |
|---|---|
| 계정 정보 | 캡처의 계정 이메일은 가림 처리 |
| API Key·토큰 | 도구의 Connection에만 저장하고 문서와 캡처에는 노출하지 않음 |
| Slack 정보 | 워크플로우 증빙에 필요한 워크스페이스·채널·메시지만 캡처하고 연결 토큰은 노출하지 않음 |
| 프로젝트 1 데이터 | 원본 링크, 본문 추출 성공 여부, 결과 안내를 Slack 스레드 안에서만 처리 |

# 자동화 도구 비교 구현 보고서 (Make vs n8n)

## 1. 사용한 도구

| 항목          | Make                   | n8n                                  |
| ----------- | ---------------------- | ------------------------------------ |
| 형태          | 클라우드 SaaS (us2 리전)     | 클라우드 호스팅(n8n Cloud) / 자가호스팅 가능       |
| 플랜          | Free                   | 체험판(14일, 1,000 executions)           |
| 시나리오/워크플로우명 | 프로젝트1 지원서 자동 심사 (Make) | 프로젝트1 지원서 자동 심사 (n8n)                |

## 2. 공통 워크플로우

동일한 업무를 두 도구로 같은 구조로 구현했다.

**업무**: AI 스터디 지원서 접수 자동 심사 — 지원자가 Google Form을 제출하면 점수를 자동 판정해 합격/불합격 시트로 나눠 기록하고, 합격자는 Slack에 알린다.

```text
Google Form 제출
  → (응답 시트에 새 행 발생)
  → Trigger: 새 행 감지
  → 조건 분기: 점수 >= 80 ?
      ├ 예   → 합격자 시트에 행 추가 + Slack 합격 알림
      └ 아니오 → 불합격 시트에 행 추가
```

### 구현 대응표

| 단계 | Make | n8n |
|---|---|---|
| Trigger | Google Sheets – Watch New Rows (설문지 응답 시트1) | Google Sheets Trigger – rowAdded (설문지 응답 시트1) |
| 분기 | **Router** + 경로별 필터 2개(`점수 >= 80` / `점수 < 80`) | **IF** 노드 1개(`점수 >= 80`) → true/false 두 출력 |
| Action 1 | Google Sheets – Add a Row (합격자_Make) | Google Sheets – Append (합격자_n8n) |
| Action 2 | HTTP – Make a request(POST) → Slack Incoming Webhook | Slack – Send Message (채널 지정) |
| Action 3 | Google Sheets – Add a Row (불합격_Make) | Google Sheets – Append (불합격_n8n) |
| 실행 주기 | 15분 간격(무료 플랜 최소값) + 수동 Run once | 1분 간격(Every Minute) |

### 실행 결과 (실측)

두 도구 모두 **양쪽 분기 경로가 각각 1회 이상 실제로 실행**된 것을 시트와 Slack에서 확인했다.

| 도구 | 합격 경로 | 불합격 경로 | Slack 알림 |
|---|---|---|---|
| n8n | 합격자_n8n — 박민수(90), 정우성(95) | 불합격_n8n — 최지은(55) | 3건 수신 |
| Make | 합격자_Make — 김철수(85) | 불합격_Make — 이영희(60) | 1건 수신 |

### 캡처 파일 매핑

| 요구 항목 | 캡처 파일 |
|---|---|
| n8n 워크플로우 구성 화면 | `n8n_프로젝트1_워크플로우.jpg` |
| Make 워크플로우 구성 화면 + 실행 결과 | `Make_프로젝트1_워크플로우_실행이력.jpg` (Diagram 탭 + History "Success" 로그) |
| 실행 결과(원본 데이터) | `시트_설문지원본응답.jpg` |
| 실행 결과(분기별 기록) | `시트_합격자_Make.png`, `시트_불합격_Make.png`, `시트_합격자_n8n.png`, `시트_불합격_n8n.png` |
| 실행 결과(Slack 알림) | `Slack_전체_알림.jpg` |

## 3. 구현 과정 요약

### Make
1. 시나리오 생성 → Google Sheets(Watch New Rows) 트리거 배치, dev-team 계정으로 Google 연결 생성
2. Router 추가 후 경로 2개 생성, 각 경로 첫 모듈에 필터 지정(`Numeric: greater or equal 80` / `less than 80`)
3. 각 경로에 Add a Row 모듈 배치, 트리거 출력 토큰을 컬럼에 매핑
4. Slack 알림은 **Incoming Webhook + HTTP 모듈**로 구현(사유는 5항 참조)
5. 저장 → Run once로 검증

> 실무 팁: 모듈을 하나씩 클릭해 붙이는 대신 **블루프린트 JSON을 작성해 `⋮ → Import blueprint`로 한 번에 생성**하면 트리거·Router·필터·매핑까지 통째로 만들어진다. 본 과제에서도 이 방식으로 구성했고, 이후 연결(Connection)만 지정하면 바로 동작했다.

### n8n
1. 새 워크플로우 생성 → 노드 JSON을 캔버스에 붙여넣어 전체 구조 한 번에 생성
2. Google Sheets Trigger / IF / Sheets Append ×2 / Slack 노드에 자격증명 지정
3. Publish(활성화) → 폼 응답 제출로 검증

## 4. 비교 항목

| # | 비교 항목 | Make | n8n |
|---|---|---|---|
| 1 | **분기 표현 방식** | Router로 경로를 시각적으로 늘리고 **경로마다 필터**를 단다. 3갈래 이상으로 늘리기 쉽다 | IF 노드가 **true/false 두 출력**을 갖는다. 3갈래 이상은 Switch 노드로 교체해야 한다 |
| 2 | **최소 실행 주기(무료)** | 15분 | 1분 |
| 3 | **커넥터/인증 안정성** | Google Sheets는 정상. **Slack·Gmail OAuth가 반복 실패**(`Resource not found`, 인증 대기 페이지 `Not found`) | Google Sheets·Gmail·Slack 모두 OAuth 성공(1회 재시도 필요했음) |
| 4 | **워크플로우 이식성** | 블루프린트 JSON **파일**을 export/import. 구조·매핑·필터까지 보존, 연결만 재지정 | 노드 JSON을 **클립보드로 복사·붙여넣기**. 파일 없이 즉시 이식 가능 |
| 5 | **데이터 매핑 문법** | 컬럼 인덱스 토큰(`{{1.\`1\`}}`) 중심. GUI로 토큰을 끌어다 쓰는 방식 | JS 표현식(`{{ $json.Subject }}`, 정규식·`.replace()` 등) 사용 가능해 **문자열 가공에 강함** |
| 6 | **실행 로그/디버깅** | 시나리오 History에서 번들 단위 확인. 모듈별 입출력 데이터 열람 | Executions + 노드별 INPUT/OUTPUT을 Schema/Table/JSON으로 열람. **노드 단위 부분 실행(Execute step)** 가능 |
| 7 | **에러 처리** | 모듈 우클릭 → error handler 경로 추가 | 노드 설정의 `On Error → 에러 출력` + `Retry On Fail` 내장 |
| 8 | **무료 플랜 한도** | 1,000 ops/월 | 체험 1,000 executions / 14일 (이후 유료 또는 자가호스팅) |

## 5. 각 도구의 장단점

### Make
**장점**
- Router 중심의 분기 구조가 한눈에 보인다. 경로를 늘려도 캔버스가 읽힌다.
- 블루프린트 파일로 시나리오를 통째로 백업·이관할 수 있다.
- 모듈 설정이 폼 기반이라 표현식을 몰라도 대부분 구성 가능하다.

**단점**
- 이번 환경에서 **Slack·Gmail OAuth 커넥터가 계속 실패**했다. Slack은 user/bot 두 타입 모두 `Resource not found`, Gmail도 동일 증상이었다. 결국 Slack은 Incoming Webhook을 HTTP 모듈로 호출하는 방식으로 우회했다.
- 무료 플랜의 최소 실행 간격이 15분이라 "즉시 반응"에는 부적합하다.
- 문자열 가공(정규식 등)이 함수 문법에 묶여 있어 복잡한 파싱에는 불편하다.

### n8n
**장점**
- 자격증명 연결이 안정적이었다(Google·Gmail·Slack 모두 성공).
- 노드 안에서 **JS 표현식**을 쓸 수 있어 정규식 파싱, 날짜 변환 같은 처리가 자유롭다.
- 노드 단위로 부분 실행하며 디버깅할 수 있고, 입력/출력 스키마를 바로 확인할 수 있다.
- 워크플로우를 클립보드 JSON으로 즉시 복제·이식할 수 있다.

**단점**
- IF 노드는 2갈래 고정이라 다분기는 Switch로 바꿔야 한다.
- 클라우드는 체험 기간·실행 횟수 제한이 있다(대신 자가호스팅으로 무제한 운영 가능).
- Google Sheets 노드는 시트 헤더가 바뀌면 "Column names were updated" 경고와 함께 실패하므로 컬럼 스키마를 고정해야 한다.

## 6. 어떤 상황에 적합한가 (의견)

- **Make가 적합한 경우**: 비개발 직군이 다갈래 분기 업무를 시각적으로 설계·인수인계해야 할 때. 분기가 3개 이상이고 각 경로 조건이 서로 다른 워크플로우일수록 Router의 가독성이 이점이다. 단, 사내에서 쓰는 SaaS 커넥터가 정상 연결되는지 **파일럿으로 먼저 확인**할 것을 권한다.
- **n8n이 적합한 경우**: 데이터 가공(파싱·정규식·집계)이 섞여 있거나, 실행 간격을 짧게 가져가야 하거나, 비용을 장기적으로 고정하고 싶을 때. 자가호스팅하면 실행 횟수 제한이 없고 메일 본문 같은 민감 데이터를 외부 SaaS에 태우지 않을 수 있다.
- **이번 과제 기준 결론**: 두 도구 모두 동일 워크플로우를 문제없이 구현했지만, **커넥터 인증 안정성과 표현식 자유도에서 n8n이 우세**했다. 그래서 프로젝트2(금전 메일 수집)는 n8n으로 구현했다.

## 7. 유료 기능 사용 여부

유료 결제 없이 전 과정을 완료했다. Make는 Free 플랜, n8n은 체험 플랜 범위 내에서 구현·검증했고, Slack은 Incoming Webhook(무료), Google Sheets/Forms도 무료 범위다.

> 참고: n8n 체험 기간이 끝난 뒤에도 같은 워크플로우를 계속 쓰려면 **n8n 자가호스팅**(Docker 1컨테이너)으로 옮기면 비용 없이 운영할 수 있다. 워크플로우 JSON을 그대로 붙여넣으면 이관된다.

## 8. 보안 처리

- 제출 캡처의 계정 이메일은 일부 가림 처리한다.
- Slack Incoming Webhook URL은 문서·캡처에 노출하지 않는다(캡처 시 마스킹).
- 스프레드시트 ID는 문서에 전체를 적지 않는다(`1LLY80…QKX8`).
- 기록 대상 데이터는 과제용 가상 인물(김철수·이영희 등)만 사용했다.

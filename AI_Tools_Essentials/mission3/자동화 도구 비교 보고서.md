# 자동화 도구 비교 구현 보고서 (Activepieces vs Pipedream)

## 1. 사용한 도구

| 항목 | Activepieces | Pipedream |
|---|---|---|
| 형태 | 오픈소스(MIT) 노코드 빌더. **Cloud 무료 플랜** 사용(자가호스팅도 가능) | 서버리스 워크플로우 SaaS(2026년 Workday 인수). **Free 플랜** 사용 |
| 플랜(실측) | Free — 카드 등록 없음, 일일 크레딧 갱신 | Free — 월 100 credits(1 credit = 30초 연산), 활성 워크플로우·연결 계정 수 제한, 이벤트 이력 제한 |
| 워크플로우명 | `P1 링크 본문 추출 (Activepieces)` | `P1 링크 본문 추출 (Pipedream)` (v34 Active) |
| 연동 | Slack(Lea-Loft 워크스페이스) `#link-inbox`, HTTP(jina reader) | 동일 |

## 2. 공통 워크플로우

**업무**: Slack 채널에 링크를 올리면 링크를 열어 본문을 가져오고, 읽을 수 있었는지에 따라 같은 메시지의 스레드에 결과를 달아 준다. (프로젝트 2 "링크 → AI 요약 → Lea-Loft 발행" 파이프라인의 앞부분.)

```text
Slack #link-inbox 새 메시지                       ← Trigger (Events API, 즉시)
  → URL 추출 (메시지 텍스트 <url|표시> 형식에서)
  → Action 1: 본문 추출 — GET https://r.jina.ai/{url}   (키 없이 본문을 마크다운으로)
  → 조건 분기: 본문 추출 성공?  (응답에 "Warning: Target URL returned error"가 없음)
      ├ 성공 → Action 2: 스레드 답글 "✅ 본문 추출 성공 — 제목"
      └ 실패 → Action 3: 스레드 답글 "❓ 본문 추출 실패 — 직접 확인 필요"
```

- 성공 경로 테스트 링크: 일반 문서 페이지(Wikipedia `Automation`, n8n 문서)
- 실패 경로 테스트 링크: YouTube(로그인 벽 → jina가 401 경고 반환)
- 두 도구가 같은 채널을 보므로 링크 하나에 답글이 도구별로 하나씩(총 2개) 달린다. 서로의 답글에 다시 반응하지 않도록 봇·스레드 메시지는 무시한다(§3).

### 구현 대응표

| 단계 | Activepieces | Pipedream |
|---|---|---|
| Trigger | Slack – **New Message Posted to Channel** (채널 ID 지정, `Ignore Bot Messages` 켬) | Slack – **New Message In Channels (Instant)** (`Ignore Bots`·`Ignore replies in threads` 켬) |
| URL 추출 | **Text Helper – Find** 피스, 정규식 `https?://[^\s\|>]+` | 별도 단계 없음 — HTTP 단계 URL 필드에 **JS 표현식** `{{steps.trigger.event.text.split('<')[1].split('\|')[0].split('>')[0]}}` |
| 본문 추출 | **HTTP – Send HTTP request** GET, 헤더 `Accept: text/plain` | **HTTP / Webhook – Send GET Request** |
| 분기 | **Router** 3분기: ① `본문 추출 성공`(body가 Warning 미포함 AND 텍스트에 http 포함) ② `링크 없음(무시)`(텍스트에 http 없음, 빈 분기) ③ Otherwise = 실패 | **Filter** — `End if` 본문이 "Warning: Target URL returned error" **포함**하면 종료. 답글 문구는 답글 단계에서 **삼항식**으로 성공/실패를 나눔 |
| 성공 Action | Slack – Send Message To A Channel (Reply to Thread = 트리거 ts) | Slack – Reply to a Message Thread → Filter 통과 → Slack – Add Emoji Reaction(`:link:`) |
| 실패 Action | Otherwise 분기의 Slack – Send Message(❓ 문구) | 같은 답글 단계가 ❓ 문구로 게시 → Filter에서 종료 |

> Pipedream 무료 플랜에는 **If/Else·Switch 분기가 없다(Advanced 유료)**. 과제 예시의 Zapier처럼 Filter(통과/종료)로 분기를 구현했고, 실패 경로의 사용자 안내는 답글 텍스트를 조건식으로 바꾸는 방식으로 보완했다. Activepieces는 Router로 다분기를 무료로 만든다.

### 실행 결과 (실측, 2026-08-27 00:20~00:24)

| 도구 | 성공 경로 | 실패 경로 | 비고 |
|---|---|---|---|
| Activepieces | Wikipedia 링크 → `본문 추출 성공` 분기 실행, 스레드 답글 (Run 7s) | YouTube 링크 → `Otherwise` 분기 실행, ❓ 답글 (Run 12s) | 존재하지 않는 도메인 링크 1건은 HTTP 422로 실행 실패(§4-7) |
| Pipedream | Wikipedia 링크 → 답글 ✅ → Filter 통과 → `:link:` 리액션 (7.6s) | YouTube 링크 → 답글 ❓ → Filter **EXIT** (8.2s) | 동일 422 실패 1건 |

양쪽 모두 두 분기 경로가 각각 1회 이상 실제로 실행됐다.

## 3. 구현 과정 요약

### Activepieces
1. 플로우 생성 → Slack 트리거 선택 → Slack OAuth 연결(Lea-Loft). 첫 연결은 `not_authed`로 토큰이 저장되지 않아 **재연결**이 필요했고, 채널 드롭다운이 로드 오류라 **채널 ID를 직접 입력**했다.
2. 테스트 채널 `#link-inbox`는 Slack 웹 대신 Activepieces의 **Slack – Create Channel 액션을 테스트 실행**해 만들었다(임시 단계, 이후 제거).
3. 트리거 테스트로 실제 메시지를 샘플 데이터로 받은 뒤, Text Helper Find → HTTP → Router → Slack 답글을 데이터 선택기로 매핑했다. 입력 필드에 `{{...}}`를 직접 타이핑하면 값이 비어 들어가므로 **데이터 선택기로 토큰을 넣어야** 한다.
4. HTTP 피스는 기본적으로 JSON으로 파싱해 응답 구조가 달라지므로 `Accept: text/plain` 헤더를 붙여 문자열로 받았다.
5. Publish 후 실행. 상대 도구(Pipedream)가 사용자 토큰으로 단 스레드 답글에 반응해 헛 실행이 생겨, Router 조건에 "텍스트에 http 포함"을 더하고 링크 없는 메시지를 빈 분기로 흡수했다.
6. 편집 중 캔버스 **다중 선택 상태에서 Delete를 눌러 하위 단계가 통째로 삭제**되는 사고가 있었고, `Discard changes`로 발행본에서 복구했다.

### Pipedream
1. 프로젝트 `mission3` 생성 → 워크플로우 생성(실행 제한 시간 60초) → Slack 트리거 선택 → Slack OAuth 연결(한 번에 성공, 채널 목록 정상).
2. 트리거가 실제 메시지 이벤트를 받으면 `steps.trigger.event`로 후속 단계에서 참조된다. URL 추출은 별도 단계 없이 JS 표현식으로 처리했다 — 단, `{{ }}` 안에서 `[^…]`가 든 정규식 리터럴은 파서 오류(`Unexpected token '^'`)라 `split` 체인으로 대체했다.
3. If/Else가 유료(Advanced)임을 확인하고 Filter로 분기를 구현. 답글 텍스트는 `includes(...) ? '❓…' : '✅…'` 삼항식.
4. 리액션 단계 테스트는 같은 메시지에 이미 이모지가 있으면 `already_reacted`로 실패한다(테스트 이벤트 재사용의 한계) → 이모지를 바꿔 통과.
5. Deploy 후 실행. 상대 도구(Activepieces)의 봇 답글에 반응해 오류가 나서 트리거 옵션 `Ignore Bots`·`Ignore replies in threads`를 켜고 재배포(v34).
6. 빌더 UI가 한 박자 늦게 렌더링되고, 드롭다운의 "custom expression" 입력이 자주 초기화돼 설정에 시간이 걸렸다.

## 4. 비교 항목 (8개)

| # | 비교 항목 | Activepieces | Pipedream |
|---|---|---|---|
| 1 | **트리거 방식** | Slack Events API 즉시 트리거. 봇 메시지 무시 옵션 내장 | 동일하게 즉시. `Ignore Bots`·`Ignore replies in threads` 두 옵션 제공 |
| 2 | **조건 분기** | **Router** — 분기 N개 + Otherwise, 분기별 AND/OR 조건, 무료 | **Filter**(통과/종료)만 무료. **If/Else·Switch는 유료(Advanced)** |
| 3 | **데이터 매핑·표현식** | 데이터 선택기로 토큰 삽입(직접 타이핑 불가). 문자열 가공은 Text Helper 등 **피스**로 | 필드 안에 **JS 표현식** 자유롭게(`split`, 삼항식 등). 정규식 리터럴 일부 파싱 제약 |
| 4 | **커넥터·OAuth 안정성** | Slack 첫 연결 실패(`not_authed`) → 재연결, 채널 목록 로드 오류 → ID 수동 입력 | Slack 연결·채널 목록 한 번에 정상. 드롭다운 커스텀 입력 UI는 불안정 |
| 5 | **실행 로그·디버깅** | Runs 목록 → 캔버스 위에 단계별 Succeeded/Failed와 분기 경로가 그려짐. 단계 입력/출력 열람 | Live Events 목록 → 이벤트별 단계 결과와 Filter EXIT 표시. `Build from event`·`Replay event`로 재현. 무료는 이력 보존 제한 |
| 6 | **에러 처리** | HTTP 4xx는 단계 실패 → 실행 실패(기본). 단계 재시도·실패 시 계속 옵션은 유료 여부 미확인 | 동일하게 실행 실패. **자동 재시도는 유료(Advanced)**, 무료는 오류 알림만 |
| 7 | **무료 플랜 한도** | 카드 없음, 일일 크레딧. 이번 P1(실행 8회)로 한도 체감 없음 | 100 credits/월. P1 실행 후 크레딧 소모 확인 가능(1회 실행 ≈ 1 credit) |
| 8 | **빌더 UX·이식성** | 캔버스형(분기 시각화 좋음). 다중 선택 삭제 사고 위험. 플로우 JSON Import/Export 메뉴 | 세로 리스트형(분기가 없어 단순). 렌더링 지연. 워크플로우 복제·프로젝트 단위 관리 |

## 5. 각 도구의 장단점

### Activepieces
**장점**
- Router로 **다분기·Otherwise**를 무료로 만들고 캔버스에 경로가 그려져 과제 요구(양 분기 실행 증빙)에 딱 맞는다.
- 실행 결과가 캔버스 위에 단계별로 표시돼 어느 분기를 탔는지 한눈에 보인다.
- 오픈소스라 나중에 Docker 자가호스팅으로 무제한 운영 가능. Google Gemini·GitHub 등 피스가 있어 프로젝트 2 확장이 쉽다.

**단점**
- 표현식을 직접 타이핑할 수 없어 문자열 가공마다 피스를 하나씩 추가해야 한다.
- Slack OAuth·채널 목록 로드가 불안정했다(재연결·ID 수동 입력).
- 캔버스 다중 선택 상태의 Delete가 하위 단계 전체를 지운다 — 발행본이 있어야 복구된다.

### Pipedream
**장점**
- 필드 어디서나 JS 표현식을 쓸 수 있어 URL 추출·조건부 문구 같은 가공이 **단계 추가 없이** 끝난다.
- Slack 연결이 안정적이고 액션이 세분화돼 있다(스레드 답글·리액션 전용 액션).
- 이벤트 단위 재현(Replay/Build from event)이 디버깅에 유용하다.

**단점**
- **무료 플랜에 If/Else가 없다.** Filter로 흐름을 끊는 것만 가능해 두 경로에 서로 다른 액션을 두려면 우회가 필요하다.
- 자동 재시도·이벤트 이력 보존이 유료. 월 100 credits는 테스트 몇 번이면 눈에 띄게 줄어든다.
- 빌더 UI 반응이 느리고 드롭다운 커스텀 입력이 자주 초기화된다.

## 6. 어떤 상황에 적합한가 (의견)

- **Activepieces가 적합한 경우**: 분기가 2개 이상이고 경로마다 다른 액션을 두는 워크플로우, 비용을 0으로 고정하고 싶은 경우(클라우드 무료 → 자가호스팅), 실행 경로를 시각적으로 확인·인수인계해야 하는 경우.
- **Pipedream이 적합한 경우**: 데이터 가공이 많고 코드를 조금 써도 되는 사람이 단일 경로 파이프라인을 빨리 만들 때, 이벤트 재현·API 중심 통합이 중요할 때. 분기·재시도가 필요해지면 유료 전환 전제.
- **이번 과제 기준 결론**: 두 도구 모두 동일 워크플로우를 구현했지만, **무료 범위에서 조건 분기를 제대로 표현할 수 있는 쪽은 Activepieces**였다. 프로젝트 2(Gemini 3.5 Flash-Lite 요약·분류 → 분기 → GitHub 커밋 2회 → Slack 답글)는 분기와 다중 액션이 핵심이므로 Activepieces로 구현한다.

## 7. 유료 기능 사용 여부

프로젝트 1은 전부 무료로 완료했다(Activepieces Free, Pipedream Free, Slack 무료 워크스페이스, jina reader 무료). 유료 기능이 필요했던 지점(Pipedream If/Else·자동 재시도)은 쓰지 않고 Filter·조건식으로 대체했다. 프로젝트 2도 Google Gemini 3.5 Flash-Lite 무료 티어를 사용하므로 전 구성 요소를 무료 범위에서 운영한다.

## 8. 보안 처리

- 캡처의 계정 이메일은 가림 처리했다(Pipedream 트리거 화면). 토큰·키는 어디에도 노출되지 않는다.
- Slack 채널 ID는 비밀이 아니므로 문서에 남긴다. 워크스페이스 이름 외 조직 정보는 캡처에 없다.
- 외부 저장소 없이 Slack 안에서 완결되므로 기록되는 개인정보가 없다.

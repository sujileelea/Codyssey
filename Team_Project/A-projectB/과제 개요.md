# 뉴스 AI 파이프라인 팀 과제 개요

## 1. 미션 소개

- 데이터를 **수집 → 정제 → AI 분석 → 리포트**로 내보내는 흐름 = 데이터 파이프라인
	- 각 단계를 따로 해본 경험은 있어도 하나의 서비스로 연결하는 것은 처음
	- 뉴스 자동 수집부터 AI 요약·분석, 인사이트 리포트 생성까지 **CLI 기반 Python 애플리케이션 1개**로 완성

```text
뉴스 수집(API/RSS + 크롤링) -> raw 저장 -> 정제·중복 처리 -> clean 저장 -> AI 요약 -> AI 인사이트 분석 -> 시각화·리포트 -> CSV/Excel 내보내기
```

- 평가 포인트: "돌아가기만 하면 된다"가 아니라 **외부 API 수집과 오류 처리, raw/clean 분리 저장의 이유, AI 호출 결과의 저장·집계·시각화**까지 전체 흐름을 설명할 수 있는 것

## 2. 팀 역할

| 팀원 | 담당 파트 | 범위 |
| --- | --- | --- |
| **수지 (owner)** | 이 외 전부 | CLI 골격·설정·로깅, 뉴스 수집(RSS + 크롤링), 시각화, 리포트, 내보내기, 보너스 `list`/`show`, 통합·검증·테스트·문서·제출 |
| **혜민** | 데이터 저장/정제 | 영구 저장소(SQLite) 스키마, raw/clean 분리 저장, 정제 규칙, 중복 정책(skip/upsert), `clean` 서브커맨드 |
| **진성** | 요약 | 뉴스 요약 프롬프트·저장, `summarize` 서브커맨드(대상 선택·기요약 스킵·재요약), API 실패 로깅 후 스킵 |
| **경학** | 인사이트 분석 | 공용 AI 클라이언트(Gemini), 기간·카테고리 조건 종합 분석(배치→종합), 분석 결과 저장·조회, `analyze` 서브커맨드, 보너스 감성 분석 `sentiment` |

- 사용 도구·아키텍처·진행 단계·결과 요약: `수행 플랜.md`
- 실제 실행 기록·산출물: `제출물/실행 결과.md`

### 목표별 답변

> 2026-09-09 BBC News 코리아 실데이터로 전 구간을 실행한 결과 기준 · 로그·수치는 `제출물/실행 결과.md`

#### 1) API/RSS 방식과 크롤링 방식의 비교

| 구분 | API/RSS | 크롤링 |
| --- | --- | --- |
| 데이터 형태 | 구조화된 JSON/XML — 제목·링크·발행일·요약이 필드로 제공 | HTML — 원하는 요소를 선택자로 직접 추출 |
| 안정성 | 제공자가 형식을 보장해 파싱이 안정적 | 사이트 마크업이 바뀌면 선택자가 깨짐 |
| 제공 범위 | 제공자가 공개한 필드만 (RSS는 보통 본문 전문 없음) | 화면에 보이는 것은 대부분 수집 가능 (본문 전문 포함) |
| 정책·윤리 | 공개 제공 채널 — 이용 약관 범위 안에서 자유로움 | robots.txt·이용 약관 준수, 요청 지연과 빈도 제한 필요 |
| 구현 비용 | 낮음 (`xml.etree`·`feedparser` 등으로 몇 줄) | 높음 (요청·파싱·예외·지연·재시도) |
| 이번 과제 실측 | BBC 코리아 RSS 1회 요청으로 피드 21건(수집 10건)의 제목·요약문·링크·발행시각(RFC 2822) 확보 — **카테고리·본문 없음** | 섹션 페이지 5개 → 기사 50건 · 본문 평균 3,305자·발행시각(JSON-LD)·섹션명(=카테고리) 확보 · 본문 `<p>`의 class가 해시형이라 구조 선택자(`main p`)만 사용 |

- **결론**: 목록·메타데이터는 RSS, 본문 전문·카테고리는 크롤링으로 보강하는 조합이 안정성과 데이터 완결성을 함께 충족
	- RSS만으로는 카테고리·본문 확보 불가, 크롤링만으로는 마크업 변경 위험 → 두 방법 병행

#### 2) 외부 수집과 오류 처리

- 모든 HTTP 요청에 `timeout=10` 지정 (`collector/http_client.py`)
	- `Timeout`·`ConnectionError`·5xx: 최대 2회 재시도 / 4xx: 즉시 실패 / 요청 간 1.5초 지연
- 실패 건은 WARNING/ERROR 로깅 후 스킵, 다음 건 계속 — 한 건의 실패가 전체 수집을 중단시키지 않음
- 실측
	- `timeout=0.001` 강제 → `타임아웃 (1/2)…(2/2)` → `RSS 수집 실패` → `수집 완료: 0건 성공, 1건 실패` (종료 코드 1)
	- AI API도 같은 원칙 — 모델 종료(404)·무료 티어 한도(429)에서 건별 재시도 후 스킵, 429는 서버 안내 시간만큼 대기 후 재시도하도록 보강
- 수집 결과는 성공/실패 건수로 요약 출력 (`수집 완료: 60건 성공, 0건 실패`)

#### 3) raw와 clean을 분리 저장하는 이유

- **raw**: 수집 시각·소스·수집 방법과 함께 원본을 그대로 보관하는 append-only 기록
	- 정제 규칙 변경·버그 시 raw에서 재정제 가능 → 재현성과 감사 가능성 확보
- **clean**: 필수 필드 검증·텍스트 정규화·날짜 형식 통일·결측값 처리·중복 정책을 거친 분석용 데이터
	- 하류 단계(요약·분석·리포트)는 clean만 참조 → 데이터 계약 단순화
- 분리하지 않을 때의 문제: 정제 오류가 원본을 덮어써 복구 불가, 수집과 정제의 책임이 섞여 원인 추적 곤란
- 실측: raw 60건(크롤링 50 + RSS 10) → clean 46건
	- 여러 섹션에 실린 기사와 RSS·크롤링 중복 14건이 URL 정규화(`?at_medium=RSS…` 제거) 후 같은 URL로 판정돼 skip
	- raw는 60건 그대로 보존 → `clean --all --duplicate-policy upsert`로 언제든 재정제 가능

#### 4) AI API로 요약·분석하는 흐름

1. clean 저장소에서 대상 뉴스 선택 (`--all` · `--id` · `--unsummarized`)
2. 본문을 프롬프트 템플릿에 넣어 AI API 요청 (요약은 건별, 분석은 기간·카테고리 묶음)
3. 응답을 파싱해 저장소에 기록 (요약은 기사 행에, 분석은 별도 테이블에)
4. API 실패는 로깅 후 스킵, 이미 요약된 기사는 기본 스킵 → 비용 절감

- 실측
	- Gemini `gemini-3.5-flash-lite`(무료 티어)로 46건 요약 — 평균 3,588자 → 238자
	- 인사이트 분석: 20건 배치 3개 → 종합(reduce) 1회 → 트렌드 3·키워드 6·주요 이슈 4를 JSON Schema 응답으로 받아 `insights`에 저장
	- 감성 분석: 46건 모두 긍정/중립/부정 + score + 근거 (부정 20 · 중립 14 · 긍정 12)
	- 무료 티어 분당 15회 한도 → 호출 간격 4.5초

#### 5) 집계와 matplotlib 시각화

- 저장소에서 SQL 집계 (카테고리별 건수 · 일자별 수집 건수 · 감성 분포)
- matplotlib에 한글 폰트 지정 (macOS `AppleGothic` · Windows `Malgun Gothic` · Linux `NanumGothic`) 후 막대·선 차트를 PNG로 저장
- 리포트는 같은 집계로 품질 지표와 TOP N을 계산해 텍스트로 출력하고 차트 파일 링크
- 실측
	- `storage.count_by_category` · `count_by_collected_date` · `count_by_sentiment`가 SQL `GROUP BY` 결과를 `(라벨, 건수)` 목록으로 반환
	- `report/charts.py`가 이를 막대·선 차트로 그려 PNG 4장 저장 (카테고리별 · 일자별 수집 · 일자별 발행 · 감성)
	- macOS에서 AppleGothic 자동 선택 → 한글 축·범례 정상

## 5. 기능 요구 사항

### CLI 설계

- `argparse` 서브커맨드 기반 CLI
- 필수 서브커맨드: `fetch` · `clean` · `summarize` · `analyze` · `report` · `export`
- 각 서브커맨드에 필요한 옵션 지원 (예: `--limit` · `--category` · `--date` · `--format`)

### 뉴스 수집

- 두 가지 방법 **모두** 구현
	- 방법 1: 공개 뉴스 API 또는 RSS 피드
	- 방법 2: 뉴스 사이트 크롤링 (BeautifulSoup 또는 Selenium)
- HTTP 요청 시 타임아웃 설정과 오류 처리
- 수집 원본은 수집 시각·소스 정보·수집 방법과 함께 raw 저장소에 저장

### 데이터 정제

- 정제 규칙: 필수 필드 검증 · 텍스트 정규화 · 날짜 형식 통일 · 결측값 처리
- 중복 처리 정책(skip/upsert) 적용
- 정제 데이터는 clean 저장소에 별도 저장

### AI 요약

- AI API 호출로 뉴스 본문 요약
- 요약 대상 선택 옵션 (`--all` · `--id` · `--unsummarized`)
- API 실패 시 로깅 후 스킵, 이미 요약된 뉴스는 기본 스킵

### AI 인사이트 분석

- 조건별(기간·카테고리) 뉴스를 종합해 AI 분석 요청
- 분석 항목 2개 이상 (주요 트렌드 · 핵심 키워드 · 공통점/차이점 · 시사점)
- 분석 결과는 별도 저장해 리포트에 활용

### 시각화

- matplotlib 차트 최소 2종: 카테고리별 뉴스 수 · 일자별 수집 추이
- 한글 폰트 적용 · PNG 저장

### 리포트 생성

- 품질 지표 2개 이상 · TOP N 집계 1개 이상 · AI 인사이트 결과 포함
- 콘솔 출력 및 파일(TXT/MD) 저장

### 데이터 내보내기

- 지원 포맷: CSV · JSONL · Excel 중 최소 2개
- 필터링 옵션 (`--status summarized`)

### 설정 및 로깅

- 설정 파일(`config.json`)로 API 키·뉴스 소스 URL·중복 정책 관리
- `logging` 모듈로 INFO/WARNING/ERROR 레벨 로그 기록

### 데이터 저장

- 영구 저장소(SQLite 또는 JSONL 파일) 필수
- 메모리(List/Dict)만으로 데이터 관리 금지

### 코드 구조

- 단일 파일 작성 금지
- 최소 4개 이상의 모듈로 분리

## 9. 결과 예시 (참고용 — 정답 아님)

### 뉴스 수집

```text
$ python main.py fetch --source naver --limit 20

[INFO] 뉴스 수집 시작: source=naver, limit=20
[INFO] 수집 완료: 20건 성공, 0건 실패
[INFO] raw 저장소에 저장 완료
```

### AI 요약

```text
$ python main.py summarize --unsummarized --limit 10

[INFO] 요약 대상: 10건
[INFO] [1/10] ID=42 요약 완료 (328자 → 89자)
[INFO] [2/10] ID=43 요약 완료 (512자 → 102자)
...
[INFO] 요약 완료: 10건 성공, 0건 실패
```

```text
$ python main.py analyze --date-from 20XX-01-01 --date-to 20XX-01-10 --category IT

[INFO] 분석 완료

- AI 기술의 산업 전반 확산 가속화
- 클라우드 기반 서비스 경쟁 심화
```
